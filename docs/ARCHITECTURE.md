# Архитектура LinkerMor

## Принцип

Один процесс, много чатов. Контекст определяется `chat_id`; данные и настройки
одного чата не могут попасть в другой.

## Структура

Ограничение проекта: максимум два уровня — `root/folder/file.py`.

| Папка | Назначение |
|---|---|
| `core/` | конфигурация, логирование, ошибки, реестр модулей, сборка приложения |
| `database/` | движок, сессии, базовый класс моделей |
| `cache/` | контракт кеша, реализация в памяти, построение ключей |
| `middlewares/` | сквозная обработка апдейтов |
| `guards/` | фильтры хендлеров aiogram |
| `ui/` | кнопки, клавиатуры, реестр меню |
| `texts/` | Custom Texts, плейсхолдеры, работа с entities |
| `settings/`, `permissions/`, `resolver/`, `sender/` | центральные сервисы |
| `mod_*/` | модули: каждый со своими handlers, service, repo, models, menu |
| `tasks/` | фоновые задачи |
| `migrations/`, `migrations_versions/` | Alembic; ревизии лежат плоско |

## Конвейер обработки апдейта

```
Update
  → LoggingMiddleware      correlation id, chat_id, user_id в контекст логов
  → ErrorMiddleware        пользователь никогда не видит traceback
  → DbSessionMiddleware    одна сессия на апдейт из общего пула
  → ChatContextMiddleware  чат, участник, настройки
  → PermissionsMiddleware  роль в этом чате, права бота в этом чате
  → роутеры модулей в порядке ModuleSpec.priority
```

## Реестр модулей

Модуль описывает себя объектом `ModuleSpec` в `spec.py`: роутер, приоритет,
настройки, тексты, пункты меню, модели, требуемые права бота. `core/registry.py`
собирает спеки, отвергает конфликты имён и приоритетов, подключает роутеры.

Добавление модуля — папка и одна строка в `ENABLED_MODULES`. Ядро не меняется.

## Изоляция данных

Три уровня защиты:

1. **Схема.** Таблицы с данными чата наследуют `ChatScopedMixin`; `chat_id`
   входит в первичный или уникальный ключ.
2. **Кеш.** Сущности разделены на `ChatEntity` и `GlobalEntity`. Ключ для данных
   чата строится только функцией `chat_key(entity, chat_id, ...)`, где `chat_id`
   обязателен. Функции, собирающей ключ чата без `chat_id`, в проекте нет.
3. **Тесты.** Изоляция проверяется автоматически, включая обязательный сценарий
   «изменили чат A → чат B не изменился → после перезапуска оба значения на месте».

## Архитектурные тесты

Договорённости проекта проверяются автоматически, а не держатся на внимании:

| Тест | Что стережёт |
|---|---|
| глубина структуры | ограничение `root/folder/file` |
| ключи кеша | невозможность собрать ключ чата без `chat_id` |
| хардкод текстов | всё, что видит пользователь, идёт через Custom Texts |
| неиспользуемые тексты | реестр не зарастает мёртвыми ключами |
| секреты | `.env` исключён из git, в примере нет настоящего токена |

## Кеш и инвалидация

При одном экземпляре приложения кеш живёт в памяти процесса, поэтому инвалидация
мгновенная и Redis для неё не нужен. Контракт вынесен в протокол `CacheBackend`,
так что переход на несколько экземпляров — замена реализации, а не переписывание
сервисов.

Redis используется для того, что кешем не является: хранение состояний FSM между
перезапусками, счётчики флуда со сроком жизни, токены длинных callback.

## Права

`PermissionService` отвечает на вопрос «может ли этот человек сделать это
в этом чате». Роль всегда берётся для конкретного `chat_id`; единственная
глобальная проверка во всём проекте — принадлежность к `OWNER_IDS`.

Проверяются и права самого бота: если Telegram не выдал разрешение, команда
сообщает об этом текстом с названием права, а не падает с ошибкой API.

Защита цели: администратор не может применить меру к равному или старшему,
к себе и к самому боту — иначе два администратора способны заблокировать
друг друга.

Анонимный администратор приходит от служебного бота `GroupAnonymousBot`,
и личность Telegram не раскрывает. Писать анонимно может только
администратор, поэтому такой отправитель получает права администратора.

## Определение цели команды

`UserResolver` понимает четыре источника: ответ на сообщение, entity
`text_mention`, `@username` и числовой ID. Ответ имеет приоритет над
аргументом, поэтому остаток строки становится причиной наказания.

Ограничение Bot API: метода «`@username` → `user_id`» не существует. По
username находятся только те, кого бот уже видел, — их данные попадают в
справочник из каждого обработанного апдейта.

Ответ на пост от имени канала даёт цель с признаком `is_chat`: такой
отправитель блокируется отдельным методом `banChatSenderChat`.

## Отправка сообщений

`Sender` — единственный способ отправить сообщение. Соблюдает два лимита
Telegram: около 30 сообщений в секунду в сумме и примерно одно в три
секунды в один чат. Повторяет отправку после требования подождать и не
роняет обработку, если бота исключили из чата.

## Настройки и тексты

Источник истины — реестры в коде. В базе лежат только переопределения.

**Настройки** (`settings/`): `SettingDef` объявляет ключ, тип, значение по
умолчанию, границы и допустимые варианты. `SettingsService` — единственная
точка доступа: читает через кеш, при записи проверяет значение, пишет в
журнал изменений и сбрасывает кеш только своего чата.

**Тексты** (`texts/`): цепочка резолва «текст чата → глобальный текст →
значение по умолчанию». Пустых мест не остаётся никогда. Текст с неизвестным
плейсхолдером отклоняется при сохранении, а в рантайме вырезается.

**`EntityText`** — текст вместе с форматированием. Подстановка значений
пересчитывает offsets, поэтому жирный шрифт и премиум-эмодзи не съезжают.
Значением плейсхолдера может быть не только строка, но и `EntityText`:
упоминание пользователя без username возможно только через `text_mention`.

Следствие: добавление настройки или текста не требует миграции базы, а
«сохранение после перезапуска» выполняется само — значение либо в базе,
либо в определении.

## Возможности Bot API 10.3

Используются нативно, без эмуляции:

- `InlineKeyboardButton.style` — цвет кнопки: `primary` (синий), `success`
  (зелёный), `danger` (красный), `link`;
- `icon_custom_emoji_id` — премиум-эмодзи на кнопке;
- `custom_emoji` entities в тексте сообщений.

Тексты хранятся парой «текст + entities». При подстановке плейсхолдеров offsets
пересчитываются, поэтому форматирование и премиум-эмодзи не разъезжаются.
